## 0. 结论速览

| 项 | 结论 |
|---|---|
| 可行性 | **全部打通**。读侧 3 个口（列表/楼层/热搜）游客态即可用；写侧 3 个口（发/回复/点赞）路由已验证存在（`code=301` 需登录） |
| 最大收益 | **评论数省一个请求**（列表自带 `totalCount`）；**排序档位由服务端给出**（`sortTypeList`），不用像酷狗那样硬编码 |
| 最大障碍 | 无。加密层（weapi/eapi）本仓已有且已在 A2/A3/G13 验证过 |
| 与酷狗能否复用 | **UI 与 `Comment` 模型可复用；协议层零共用**（端点、加密、响应包裹全不同） |

| 建议分期 | N1 读侧（低风险，游客可跑）→ N2 写侧（需登录）→ N3 热搜（独立小口） |

## 2. 响应形态（抄代码前必读）

### 2.1 E1 列表：`data` 包裹，不是顶层平铺

```
{ code: 200, message: '成功',
  data: {
    comments: [...], totalCount: 28883, hasMore: true, cursor: ...,
    sortType: 99, sortTypeList: [...], commentsTitle: '全部评论',
    commentsTitle / currentCommentTitle / lottery / style /
    bottomAction / likeAnimation / linkJumps / newReplyExpGroupName / expandCount
  } }
```

评论项关键字段：`commentId` `content` `time`(毫秒) `timeStr`（**已是「9分钟前」「2024-12-08」这类可读文本**）
`likedCount` `liked` `favorited` `parentCommentId` `beReplied[]` `replyCount`
`ipLocation.location`（IP 属地）`showFloorComment.replyCount`（楼层数）
`user.nickname` `user.avatarUrl` `user.vipType` `user.authStatus` `user.expertTags`
`pickInfo`（精选）`decoration.repliedByAuthorCount`（作者回复数）`tag`

> ⚠️ **同一平台两套包裹**：老口 `/weapi/v1/resource/comments/{threadId}` 是**顶层平铺**，新口 `/eapi/v2/resource/comments` 是 **`data` 包裹**。探针第一轮就是按老口习惯读顶层 `comments`，拿到空列表。

### 2.2 E2 楼层：数据同样在 `data` 下

```
{ code: 200, message: '获取成功',
  data: { ownerComment: {...}, currentComment: null,
          comments: [...], hasMore: false, totalCount: 102,
          time: ..., bestComments: [...] } }
```

- `data.ownerComment` = 父评论本身（不必再查一次）
- `data.comments` = 楼层回复；`data.bestComments` = 精选回复
- 楼层项带 `parentCommentId`（= 父评论 id）与 `beReplied[]`（被回复者昵称 + 原文）

> 踩坑留档：我先后试了 `/weapi/v1/resource/comments/A_PL_0_{cid}` 与 `{parentCommentId}` 参数两种写法，**12 条候选全部 `total=0`** —— 因为 `A_PL_0_` 是**歌单**的 thread 前缀，跟楼层无关。楼层是独立端点。拿到正确端点后响应有 22KB 却仍显示 0 条，原因是**又按老口读了顶层 `comments`**，实际在 `data.comments`。

### 2.3 E6 热搜：形态简陋

10 条 `{ first: '茶汤', second: 1, third: null, iconType: 1 }` —— `first` 是词，`second` 实测恒为 `1`、`third` 恒 `null`（含义不明，可能是排行榜标记位）。**没有热度值**。只有 10 条，无分页。

## 3. 排序与分页（E1 的核心）

### 3.1 档位由服务端给出，别硬编码

```
sortTypeList: [
  { sortType: 1, sortTypeName: '按推荐排序', target: 'order_by_alg'  },
  { sortType: 2, sortTypeName: '按热度排序', target: 'order_by_hot'  },
  { sortType: 3, sortTypeName: '按时间排序', target: 'order_by_time' },
]
```

- **`sortType=1` 必须归一化成 `99`** 再发（参考实现：`if (sortType === 1) sortType = 99`）
- 三档内容实测不同：
  - `99` 推荐 = 热评 + 最新混排（11 条里含 8 条热评 + 3 条最新）
  - `2` 热度 = 纯按赞数
  - `3` 时间 = 最新倒序

### 3.2 `cursor` 三种形态完全不同

| sortType | 服务端生成 cursor 的规律（**只供理解，不要自己拼**） |
|---|---|
| 99 推荐 | 毫秒时间戳（`1790422846204`） |
| 2 热度 | 字符串 `normalHot#<n>`，且 **n 由服务端自算、会跳**（实测 `20 → 40 → 110`，不是等差） |
| 3 时间 | 毫秒时间戳（= 本页末条的 `time`） |
| 首页 | 传 `'0'` |

> ⚠️ **2026-09-27 修正（推翻下面的旧结论）**：下一页 cursor **就直接用响应里的
> `data.cursor`**，三档连翻 3 页实测**零重复、能收敛**：
>
> | 档位 | 第 1 页 | 第 2 页 | 第 3 页 |
> |---|---|---|---|
> | 99 推荐 | 26 条 → `1790422846204` | 19 条 → `1790310302786` | 18 条 → `1790085672030` |
> | 2 热度 | 20 条 → `normalHot#20` | 20 条 → `normalHot#40` | 20 条 → `normalHot#110` |
> | 3 时间 | 18 条 → `1790422846204` | 19 条 → `1790310302786` | 18 条 → `1790085672030` |
>
> 而**自己按 `pageNo * pageSize` 拼 offset 是错的**，两个原因：
> ① **响应条数不受 `pageSize` 控制**（要 20 时推荐档给 26、时间档给 18、热度档给 20）；
> ② 热度档的 n 是服务端自算的跳跃序列，拼出来的必然错位。
> 实测「拼 offset」时推荐档第二页回了 336 条（明显错乱），而回传 `data.cursor` 始终正确。
>
> 旧结论（**作废**）：~~响应返回的 `cursor` 不等于下一页要传的 cursor，别直接回传~~
> —— 这条是 9/26 用 `pageSize=3` 的小样本测出来的，那次可能是因为 pageSize 过小
> 服务端忽略了 cursor。以本次三页链式的实测为准。

## 5. 对现有插槽的影响（本轮最重要的设计结论）

上一轮刚把评论能力收口成「入参 `Track`」，网易侧恰好**验证了这个决定**：

✅ **`songComments(Track)` 直接可用** —— 网易的 `threadId` 就是 `'R_SO_4_' + track.id`，不需要像酷狗那样回搜解析。反过来看，如果签名还是 `songComments(String mixSongId)`，网易就得额外塞一个「mixSongId 其实是 songId」的假概念。

✅ **`CommentPage.childrenId` 保留是对的** —— 两源语义不同：酷狗是**不透明 token**（UI 原样回传），网易是**可从 Track 重算的派生值**。UI 两种都不解读，所以同一字段能装下。

❌ **`CommentSort` 枚举需要改** —— 现在是硬编码 `all / hottest / barrage`：
- 网易档位是 **3 个且由服务端给出**（推荐/热度/时间），没有弹幕；
- 酷狗是 2 个**接口**（全部/最热）+ 弹幕这个独立池，档位语义是「请求路由」；
- 硬编码枚举表达不了「档位由实现给出」这件事，且 `barrage` 对网易是伪档位。

按项目既有惯例（`NewAlbumFeedSource.albumRegions`、`ArtistListSource.artistGenderOptions` 都是「选项由实现给出、首项即默认、UI 只渲染 chips 并原样回传 id」），评论档位应当同构：

```dart
// 方向（不是最终代码）
abstract interface class CommentReadSource {
  /// 评论档位（首项即默认）；各源原生值，UI 只渲染并按 id 回传。
  List<({String id, String label})> get commentSortOptions;

  Future<CommentPage> songComments(Track track, {String sort = '', ...});
}
```

这样酷狗给 `[('all','全部'),('hottest','最热'),('barrage','弹幕')]`，网易给 `[('1','按推荐排序'),('2','按热度排序'),('3','按时间排序')]`，UI 一行不用改。

> 这是个**接口变更**（`CommentSort` 枚举退役），建议放在 N1 一起做，别先按枚举写一版再改。

**其余可复用**：`Comment` 模型（id/user/content/likeCount/timeLabel/avatarUrl/replyCount/location/badges）字段基本能对上；`comment_location` → `ipLocation.location` 映射即可；`badges` 需要一个新的网易判定函数（`vipType`/`authStatus`/`expertTags`），**不要试图复用酷狗的 `_plateId` 判定链**。

## 7. 风险与未验证项

1. **写侧未真实验证**（唯一需要账号的一步）。三个写口都只验到 `301 需登录`，真实提交行为未测。按酷狗的先例，留给你本人点一次。
2. **eapi 组合未复验**：现有 eapi 只跑过 `eapi/song/*`，评论口是 `eapi/v2/resource/comments`。加密与 host 一致，但**首次调通要单独确认**。
3. **风控未观测**：本轮约 30 个只读请求，无 `-460`、无验证码。写侧未知。
4. **`showInner` 未生效**：传了 `true`，但 `showFloorComment.comments` 仍为 `null` —— 楼层必须单独拉 E2。参数是否还有别的效果（如内嵌 `beReplied`）未深究。
5. **`second`/`third` 语义不明**：热搜返回字段只有 `first` 有值，**不要编造热度值**（能显示的就是这 10 个词）。
6. **未做的对照**：`/api/v1/resource/comments/{threadId}`（老口）与 `eapi/v2/resource/comments`（新口）的字段差异只粗略看过。N1 建议**只用新口**（有 `sortTypeList`/`hasMore`/`totalCount`），老口保留作对照。

## 8. N1 实施顺序（开工清单）

### 第 0 步：两处插槽重整（先做，否则后面返工）

**① 排序档位化 —— `CommentSort` 枚举退役**

现状 `CommentReadSource.songComments(Track, {CommentSort sort})` 是硬编码枚举，表达不了
「档位由服务端给出」。按项目既有惯例（`NewAlbumFeedSource.albumRegions` /
`ArtistListSource.artistGenderOptions`：**选项由实现给出、首项即默认、UI 只渲染并原样回传 id**）：

```dart
List<({String id, String label})> get commentSortOptions;   // 首项即默认
Future<CommentPage> songComments(Track track, {String sort = '', ...});
```

- 酷狗给 `[('all','全部'), ('hottest','最热'), ('barrage','弹幕')]`
- 网易给服务端 `sortTypeList` 原样（`('1','按推荐排序') / ('2','按热度排序') / ('3','按时间排序')`）

代价：酷狗侧实现与测试跟着改一遍（一次性）。**不要先按枚举写一版网易再返工。**

**② 分类 / 热词拆出 `CommentReadSource`**

`classifyComments` / `hotwordComments` 现在挂读侧接口上，但**只有酷狗有**（网易无分类、无热词）。
网易 `implements` 就得写两个假方法 —— 与 `capabilities.dart` 开头那句「谁有谁 `implements`，
禁止在基类堆 `bool get hasXxx` + 空实现」直接冲突。

拆成独立能力 `CommentFilterSource`（酷狗 `implements`，网易不插，UI 自动不出 chips 行）。

### 第 1~4 步：网易侧本体

| 步 | 改动 | 要点 |

### 10.3 第 0 步：其实是**三处**插槽重整（§8 漏记了分页）

**① 排序档位化**（§8 已有，照做）
`List<({String id, String label})> get commentSortOptions`（首项即默认）+ `sort: String`。
酷狗 `[('all','全部'),('hottest','最热'),('barrage','弹幕')]`；网易吃服务端 `sortTypeList`。

**② 酷狗独有增强拆出**（§8 已有，范围扩大到 `featuredComments`）
`classifyComments` / `hotwordComments` / `featuredComments` 三者**只有酷狗有**，
留在 `CommentReadSource` 上就等于逼网易写三个空实现（与 `capabilities.dart:10` 的
「谁有谁 implements」直接冲突）。拆成 **`CommentExtrasSource`**（建议此名，因为
`featured` 不是「筛选」，叫 `CommentFilterSource` 名不副实）。
UI 侧：有该能力才渲染 chips 行与精彩评论块；网易不 implements ⇒ 自动不出。

**③ 分页双形态 —— §8 漏了这一处，必须补**（本轮新发现）

酷狗是**页码式**（`page` + 响应 `maxPage`），网易是**游标式**且三档 cursor 形态不同
（§3.2：推荐 = 数字 offset；热度 = `'normalHot#'+offset`；**时间 = 上一页末条的 `time`**）。
时间档的下一页游标**依赖上一页的 items** —— 现有 `songComments(track, page, pageSize, sort)`
签名传不进去。

设计（沿用「源差异收口在实现里」的老办法 —— 游标对 UI 不透明）：

```dart
class CommentPage {
  final String nextCursor;   // 新增：下一页游标，空 = 无下一页（酷狗恒空）
}

Future<CommentPage> songComments(Track track, {
  int page = 1, int pageSize = 20, String sort = '', String cursor = '',
});
```

- 酷狗：忽略 `cursor`，`nextCursor` 恒空 → 走原页码逻辑（**行为不变**）
- 网易：映射时算好下一页游标塞进 `nextCursor`；UI 原样回传
- UI `_pageHasMore`：`nextCursor.isNotEmpty` 优先，否则回落原 `lastPageFull && maxPage` 判断

这样 UI 只多一个「不透明字符串回传」，酷狗零影响，网易三档 cursor 全在实现里。
