## 1. EchoMusic 的请求链路

```
renderer/api/comment.ts
  → utils/request.ts（注入 Authorization: token/userid/dfid/mid/guid）
  → IPC 到主进程
  → server/ = KuGouMusicApi（Node 服务，按 module/*.js 组装请求并签名）
  → https://gateway.kugou.com/...
```

关键：**评论的签名与拼装全在 KuGouMusicApi 里**，EchoMusic 前端只传业务参数。我们这个项目没有 Node 服务，所以要按 §3 的清单在 Dart 侧复刻。

上游 host 只有三类，认清这个分类就够写代码了：

| 类型 | 形态 | 签名 | 公共参数 |
|---|---|---|---|
| A. `mcomment/v1/*` | `POST https://gateway.kugou.com/mcomment/v1/...` | android（`encryptType:'android'`） | 带全（appid/clientver/mid/dfid/uuid/clienttime + `signature`） |
| B. `m.comment.service/v1/*` | `POST https://gateway.kugou.com/m.comment.service/v1/...` | android | 同上 |
| C. `index.php` + `x-router` | `POST/GET https://gateway.kugou.com/index.php?r=xxx`，带 header `x-router: <service host>` | **notSignature**：不带 `signature`、不带默认公共参数，改用一个自定义 `key` 参数 | 仅显式传入的字段 |

C 类最容易被忽略的两点：
- **少了 `x-router` header 会 502**（实测：KWS 直接返回 `502 Bad Gateway`）。
- 它**不吃** `signature`，验证走 `key`：`signParamsKey(clienttime + mid [+ data])`。

### 2.2 写侧（全部要登录 token + `kugouid`）

**发评论**：C 类 `POST /index.php?r=commentsv3/add` + `x-router: m.comment.service.kugou.com`

```
query:  r=commentsv3/add, code, childrenid=<special_id>, childrenname=<歌曲名>,
        kugouid, ver=6, clienttoken, appid, clientver, mid, clienttime,
        key=signParamsKey(`${clienttime}${mid}${data}`),   // ← 注意 data 参与
        uuid, dfid, source
body:   data = JSON.stringify({ data: { content, album_audio_id, title, extdata, images: [] } })
        // compact：空值字段会被剔掉
```

**发楼层回复**：C 类 `POST /index.php?r=commentsv2/reply` + 同 header

```
query:  r=commentsv2/reply, code, childrenid, childrenname, kugouid, ver=6, clienttoken,
        appid, clientver, mid, clienttime,
        key=signParamsKey(`${clienttime}${mid}`),           // ← 不含 body
        uuid, dfid, extdata, content, tid, is_t, pid, source
        （无 body）
content 拼装：回复他人时若 content 不含 "//@"，会自动拼成 `${content}//@${对方昵称}:${被回复内容}`
```

**发弹幕**：`commentsv3/add` + `code=articulossong`（歌曲）/ `comments/addcomment` + `code=VIDEO_BARRAGE_CODE`（视频）。

### 2.3 风控链（写侧绕不开）

| 环节 | 模块 | 说明 |
|---|---|---|
| 挑战触发 | 任意写接口 | 响应头 `ssa-code` 或 body `error_code=20028` |
| 取验证信息 | `get_verify_info.js` → A `/verifyservice/v3/get_verify_info` POST | `eventid`，返回 `v_type`（32 短信 / 34 实名 / 36 绑手机 / 38 登录确认 / 51 账号风控 / 图形验证码） |

## 5. 风险与坑（按严重度）

1. **写侧风控（高）**。SSA 20028 一旦触发，只能走「取验证信息 → 图形码/短信 → `sidedt` 提交」。`sidedt` 依赖 `generate_simulate.js` 的浏览器指纹模拟，Dart 侧移植成本高、且随酷狗风控升级容易失效。
   **建议**：P1 只做「正常路径 + 失败明确降级」（提示「需在酷狗官方客户端完成安全验证」），把 `sidedt` 移植单列为技术预研，不塞进功能排期。
2. ~~lite 参数下发评论能否成功~~ → **已实测：读侧与写侧在 lite 参数（appid 3116 / clientver 11440）下都能用**。
   读侧与标准版（1005 / 20489）响应一致（只差 `tag`/`topad` 这类无关字段）；
   写侧另用「空正文 + 正确/错误 `key`」对照实验验证，路由与 `key` 签名均被接受（见 §10）。
3. **`special_id` 契约（中）**。`commentsv3/add` 必须带 `childrenid`（= 评论池的 `special_id`），它**不在 Track 上**，只能从 `cmtlist` 响应体（`body.childrenid` / `list[0].special_child_id`）里取；上游的兜底是「先拉 1 条列表解析」。而且本项目现有 `mixSongId` 是启发式搜索兜底的（`song_detail_page.dart:101-140`），**写侧不能沿用这个宽松策略**——发错歌是可见的、不可撤回的。宁可报「无法定位评论池」也不发。
4. **`index.php` 系必须带 `x-router`（中）**。缺了直接 502，且 502 长得像网络故障，容易误判。
5. **发送的 `key` 参与 body（中）**。`commentsv3/add` 的 `key = signParamsKey(clienttime+mid+data)` 里 `data` 是完整 JSON 字符串 —— 签名与 body 必须逐字节一致（`compact` 剔除空值后再算），否则静默失败。
6. **`index.php` 不吃公共参数（低）**。不能复用现有「默认参数 + signature」的注入逻辑，要单独一条请求通道。
7. **弹幕 ≠ 评论（低）**。code 不同、池不同，列表/发送接口也不同。
8. **长度限制（低）**。EchoMusic 自定评论 200 字 / 弹幕 100 字（注释明确写着「不代表服务端上限」），服务端真实上限未知，建议先照抄并在文案里留余地。
9. **网易侧（低但量级大）**。加密层能复用，端点、模型、楼层、写口都要从零做（网易写评论同样有风控），不要和酷狗评论混在一个 PR 里。

## 6. 本机连通性实测（2026-09-26，curl 直连，已清代理）

| 探测 | 结果 | 判定 |
|---|---|---|
| `POST/GET /mcomment/v1/cmtlist?mixsongid=…&code=fc4be…` | `{"err_code":10002,"msg":"error appid"}` (49B) | ✅ 通（仅缺签名） |

## 9. P0 实测结论与落地清单（2026-09-26）

### 9.1 排序：不是参数，是「两个接口」

**`cmtlist` 根本没有排序参数**。穷举实测（`sort` / `sort_type` / `sort_method` / `order` /
`orderby` / `order_by` / `hot` / `new` / `isnew` / `only_new` / `rank` / `ranktype` / `type` /
`filter` / `filter_type` / `iscmt` / `cmt_type` / `privacy` / `show_hot` / `newest` / `latest` /
`sortby`）—— 全部与不传时**逐条完全相同**。

真正的排序来自响应顶层 `tag[]` 页签：

| 页签 | 接口 | 备注 |
|---|---|---|
| 全部（`type: default`） | `POST /mcomment/v1/cmtlist` | 混合排序 |
| 最热（`type: api`） | `POST /m.comment.service/r/v1/rank/topliked` | 按点赞数，**需要 `childrenid`** |

「最热」路由实测：`/r/v1/rank/topliked` 裸打 502；而
`POST https://gateway.kugou.com/m.comment.service/r/v1/rank/topliked`（服务名前缀写法、
**不带 x-router**，与既有 `/m.comment.service/v1/cmtlist` 同风格）可用 ✅
（`/v1/rank/topliked` + `x-router: m.comment.service.kugou.com` 同样可用，实现选了前者）。

两条接口首条结果确实不同：全部 `1723639894:33512` vs 最热 `315129160:122115`。

### 9.2 响应结构是**顶层平铺**

`list` / `count` / `childrenid` / `maxPage` 都在**顶层**，没有 `data` 包裹（解析保留 `data` 兜底）。
最容易踩的坑：按 `data.list` 解析会永远拿到空列表（这个坑踩过一次）。

| 字段 | 含义 |
|---|---|
| `count` | 评论总数（与 `getcommentsnum` 同口径） |
| `childrenid` | 评论池 id（实测 = 搜索接口的 `audio_id`），**楼层与「最热」都靠它** |
| `maxPage` | 分页上限（`cmtlist` 有 = 5000；`topliked` **没有**） |
| `tag[]` | 页签定义（见 9.1） |
| `classify_list[]` | 分类（`{id,label,icon,cnt}`，P2 用） |
| `hot_word_list[]` | 热词（`{content,count}`，P2 用） |
| 评论项 `reply_num` / `comments_num` | 楼层回复数 |
| 评论项 `like.likenum` | 点赞数（也有扁平 `like_num`） |
| 评论项 `location` | IP 属地 |
| 评论项 `addtime` | 已是 `2025-12-26 19:46:04` 形态 |

楼层项另带 `tid`（= 根评论 id）、`pid`、`is_reply`；`content` 里的引用格式是 `//@昵称:原文`。

### 9.3 意外收获：SSA 20028 的触发条件

伪造设备身份会**立刻触发风控**：`dfid` 用「8 段数字」+ `mid` 用 40 位大数 → 20028；
而 `dfid='-'`（匿名值）+ 随机 mid 反而一切正常。这印证了 `DeviceIdentity` 里
「优先注册真实设备、失败退化成 `-`」那套设计的必要性。

## 10. 写口探测（2026-09-26，零副作用）

**安全设计**：所有探测请求的正文恒为空字符串 —— 即使服务端放行也不会产生任何内容。
目的只是从返回码判断「lite 参数 + `key` 签名 + `index.php` 路由」这条链路是否被接受。

| 探测 | 返回 | 判读 |
|---|---|---|
| A `commentsv3/add`，正确 `key`，空正文 | `err_code=10003 发送字数不够` | 路由 / appid / `key` 签名**全部被接受**，只差正文 |
| B 同上，但 `key` 故意写成 32 个 `f` | `err_code=20006 参数验证失败` | `key` **确实被校验**，且我们的算法正确（A/B 对照成立） |
| C `commentsv2/reply`（楼层，`key` 只算 `clienttime+mid`），空正文 | `err_code=10003 发送字数不够` | 回复口链路同样通过 |

三个请求都**没有**出现 20028 —— 游客态未被风控拦截。

**结论**：P1 的前置门槛达标 —— lite 参数下写口的签名与路由完全可用。
唯一没验证的是「带 token 真正提交」，它必然产生真实内容，留到 P1 实现时由使用者本人操作。
另外这条返回也顺带说明：**服务端对正文长度有校验**（10003），所以写入侧的本地长度校验不是自娱自乐。

实现上的三个硬约束（都来自实测，不是推测）：
1. 写口**不吃 `signature`**、也不注入公共参数 —— 必须单独一条请求通道，不能复用列表通道。
